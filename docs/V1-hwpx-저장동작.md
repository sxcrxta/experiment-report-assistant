# V-1 — 한글 for Mac 의 HWPX 저장 동작

관찰일: 2026-09-10
환경: macOS 15 (Darwin 24.6.0), 한컴오피스 한글 for Mac 12.30.0.6446 (MAC64LEDarwin)
대상: `~/Desktop/hwpx-test/실험보고서_샘플 복사본.hwpx` (2.1MB, 실제 실험보고서)
방법: 폴더를 25ms 간격으로 폴링하며 파일별 inode·크기·mtime·ctime 변화를 기록. 사용자가 한글에서 ⌘S.

---

## 1. 저장 시퀀스 (관찰된 그대로)

```
[+260.93s] created   ...복사본.BAK    inode=100564068  size=2,136,023   <- 원본과 같은 크기
[+260.93s] modified  ...복사본.hwpx   inode=100561851  2,136,023 -> 8,192
[+260.95s] modified  ...복사본.hwpx   inode=100561851  8,192 -> 2,136,029
[+260.95s] deleted   ...복사본.BAK    inode=100564068
```

정리하면 네 단계다.

1. **`<파일명>.BAK` 생성** — 원본 전체 사본
2. **원본을 제자리에서 잘라냄(truncate)** — 크기가 8,192바이트로 줄어든다
3. **원본에 새 내용을 다시 씀** — 2단계로부터 약 **20ms** 뒤
4. **`.BAK` 삭제**

## 2. 확인된 사실

### 2.1 원자적 교체가 아니다. inode 가 유지된다

저장 전후 `inode = 100561851` 로 동일하다. 임시 파일에 쓴 뒤 rename 으로 갈아 끼우는
방식이 **아니라**, 원본 파일 자체를 잘라내고 다시 쓴다.

> **계획 수정:** `IMPLEMENTATION_PLAN.md` 와 `CLAUDE.md` 에 "원자적 교체로 inode 가 바뀌므로
> 경로 기준으로 감시한다" 고 적어 두었는데, 전제가 틀렸다. 경로 기준 감시라는 결론은 유지하되
> (이름 바꾸기·폴더 이동 때문에 여전히 필요하다) **이유는 다르다.**

### 2.2 저장 도중 파일이 실제로 깨진 상태가 된다 ← 가장 중요

2단계와 3단계 사이의 약 **20ms 동안 파일은 8,192바이트짜리 잘린 ZIP** 이다.
이때 읽으면 HWPX 로 파싱되지 않거나, 더 나쁘게는 일부만 읽힌다.

25ms 폴링으로도 이 순간이 잡혔다. 즉 **이론적 위험이 아니라 실제로 마주치는 상태다.**
`CLAUDE.md` §3 "불완전한 파일을 읽지 않는다" 가 여기에 해당한다.

### 2.3 `.BAK` 파일이 잠깐 나타났다 사라진다

저장할 때마다 같은 폴더에 `<파일명>.BAK` 이 생겼다가 지워진다.
감시자가 이걸 새 문서로 착각하거나 감시 대상으로 삼으면 안 된다.
(한글 설정에 따라 `.BAK` 이 남을 수도 있다. 남는 경우도 무시해야 한다.)

### 2.4 파일 이름은 NFD 로 돌아온다

macOS 는 파일 이름을 **NFD(한글 자모가 분리된 형태)** 로 돌려준다.

```
readdirSync 가 준 이름 : "실험보고서_샘플 복사본.hwpx"   (NFD)
소스에 적은 문자열     : "실험보고서_샘플 복사본.hwpx"   (NFC)
=== 비교              : false
NFC 정규화 후          : true
```

눈으로는 같아 보이지만 `===` 가 false 다. **첫 관찰 시도가 이것 때문에 실패했다.**
저장은 정상적으로 일어났는데 감시 스크립트가 "대상 파일이 아니다" 라고 판단했다.

문서 **본문** 정규화(`src/core/document/normalize.ts`)에는 NFC 를 적용해 두었지만
**파일 이름** 은 고려하지 않았다. 2단계 FileWatcher 가 그대로 당할 수 있다.

## 3. 2단계 FileWatcher 가 지켜야 할 것

관찰에서 바로 나오는 요구사항이다.

1. **파일 이름 비교는 반드시 NFC 정규화 후에 한다.** (§2.4)
2. **저장 완료를 기다린 뒤 읽는다.** 변경 이벤트를 받자마자 읽지 않는다.
   크기가 일정 시간 이상 변하지 않을 때까지 기다리는 디바운스가 필요하다.
   관찰된 truncate→rewrite 간격이 20ms 이므로 디바운스는 그보다 충분히 커야 한다.
3. **읽기 전에 파일이 온전한지 확인한다.** ZIP 로 열리는지, `mimetype` 이
   `application/hwp+zip` 인지 확인하고, 실패하면 잠시 뒤 다시 시도한다.
   한 번 실패했다고 "문서가 깨졌다" 고 사용자에게 알리지 않는다.
4. **`.BAK` 을 비롯한 대상 외 파일은 무시한다.** 감시 대상은 사용자가 고른 그 경로 하나다.
5. **inode 변화를 추적 근거로 삼지 않는다.** 이 한글 버전에서는 inode 가 유지되지만,
   버전이나 저장 방식(다른 이름으로 저장 등)에 따라 달라질 수 있다. 경로를 기준으로 본다.

## 4. 재현 방법

```
node <관찰스크립트> <출력.json>
# 한글에서 파일을 열고 고친 뒤 ⌘S
```

관찰 스크립트는 폴더를 25ms 간격으로 폴링하며 `readdirSync` + `statSync` 로
inode·크기·mtime·ctime 을 비교한다. 파일 이름은 NFC 로 정규화해 비교한다.

## 5. 관찰이 코드의 어디에 들어갔나 (2단계 구현)

| 관찰 | 코드 | 테스트 |
| --- | --- | --- |
| §2.4 이름이 NFD 로 온다 | `src/adapters/watcher/filename.ts` (`toNfc` / `sameFilename`) — 이벤트 이름을 NFC 로 맞춰 비교 | `tests/watcher.test.ts` "파일 이름 비교" |
| §2.2 저장 도중 8KB 로 잘린다 | `fsevents-watcher.ts` 의 `waitUntilStable()` — 크기·mtime 이 조용해질 때까지 대기 | `tests/watcher.test.ts` "저장 한 번에 saved 를 정확히 한 번 낸다" (`byteSize` 가 8,192 가 아님을 확인) |
| §3-3 읽기 전 온전성 확인 | `src/adapters/hwpx/integrity.ts` — ZIP 목록 + `mimetype` 확인, 실패 시 재시도 | "저장이 끝나지 않아 계속 깨져 있으면 정직하게 알린다" |
| §2.3 `.BAK` 이 생겼다 사라진다 | `fsevents-watcher.ts` 의 이름 비교로 대상 외 파일 무시 | ".BAK 이 생겼다 사라지는 것만으로는 아무 일도 일어나지 않는다" |
| §2.1 inode 가 유지된다 | `signatureOf()` 는 **크기와 mtime 만** 쓴다. inode 를 추적 근거로 삼지 않는다 | 경로 유실 테스트 (이름 변경·폴더 이동·삭제) |

디바운스 기본값은 `quietPeriodMs = 300ms` 다. 관찰된 truncate→재작성 간격 20ms 보다 충분히 크다.
자동 테스트는 그 순서를 그대로 재현하되 값만 줄여 쓴다(40ms).

## 6. 실제 한글로 하는 확인 (V-1 통합 테스트)

자동 테스트는 관찰을 **재현**할 뿐이다. 재현이 실제와 같은지는 사람이 한 번 확인해야 한다.

```
V1_HWPX="/경로/보고서.hwpx" npm run test:v1
# 안내가 나오면 한글에서 문서를 고치고 ⌘S
```

`tests/integration/v1-hangul-save.test.ts` 가 확인하는 것

- 저장 한 번에 `saved` 가 정확히 한 번 나온다
- 감지한 시점의 파일이 온전하다 (잘린 8,192바이트를 읽지 않는다)
- 바뀐 문단만 추출되고, 그대로인 문단은 분석 대상에서 빠진다
- 감지 뒤로 원본 바이트가 프로그램 때문에 변하지 않는다

이 테스트는 `V1_HWPX` 가 없으면 건너뛰며, 기본 `npm run check` 에는 들어가지 않는다.

## 7. 한계

- 한 번의 저장만 관찰했다. 문서가 더 크거나 이미지가 많을 때 truncate→rewrite 간격이
  더 길어질 수 있다. 2단계 통합 테스트에서 여러 번 저장해 확인한다.
- "다른 이름으로 저장", "PDF 로 저장" 은 아직 관찰하지 않았다.
- 한글이 파일을 연 상태에서 잠금(lock)을 거는지는 확인하지 못했다.
  (`lsof` 호출이 폴링을 방해해 관찰 루프에서 제외했다.)

## 6. 통합 테스트 실행 결과 (2026-09-10)

`§3` 의 요구사항대로 구현한 뒤, **실제 한글 for Mac 으로 저장해서** 확인했다.
자동 테스트(`tests/watcher.test.ts`)는 관찰한 저장 순서를 파일 조작으로 재현할 뿐이므로,
그 재현이 실제와 같은지는 사람이 ⌘S 를 눌러 확인해야 한다.

### 실행

```
V1_HWPX="~/Desktop/hwpx-test/실험보고서_샘플 복사본.hwpx" npm run test:v1
```

안내가 나온 뒤 한글에서 본문 문단 하나에 글자를 덧붙이고 ⌘S 로 저장했다.

### 결과 — 통과

```
[V-1] 문단 435개 중 변경 1개 (그대로 434개, 삭제 0개)
  - [modified] 표 안 본문 문단 1개

 ✓ V-1 — 실제 한글 저장 (1)
   ✓ 저장 한 번에 saved 가 한 번 나오고 바뀐 문단만 추출된다   18364ms
```

확인된 것:

| 완료 조건 | 결과 |
| --- | --- |
| 저장 한 번에 `saved` 가 **정확히 한 번** | 통과. `.BAK` 생성·삭제와 truncate 중간 상태가 별도 이벤트로 새지 않았다 |
| 잘린 순간(8,192바이트)을 읽지 않는다 | 통과. 읽은 파일이 온전한 HWPX 였다 |
| 바뀐 문단만 추출된다 | 통과. **435개 중 1개**. 나머지 434개는 해시가 같아 분석 대상에서 빠졌다 |
| 원본 바이트가 프로그램 때문에 변하지 않는다 | 통과 |

18.4초는 대부분 사람이 저장하기를 기다린 시간이다.

### 이 결과가 뒷받침하는 것

- **디바운스가 실제 저장에서 동작한다.** `.BAK` 생성 → truncate → 재작성 → `.BAK` 삭제의
  네 단계가 `saved` 이벤트 하나로 합쳐졌다. §2.2 에서 확인한 20ms 짜리 깨진 구간을
  이벤트로 흘리지 않았다.
- **온전성 확인이 동작한다.** 잘린 8KB 상태를 읽었다면 파싱이 실패했을 것이다.
- **해싱·메모이제이션이 실제 문서에서 동작한다.** 435문단짜리 실제 실험보고서에서
  바뀐 1개만 걸러 냈다. PRD 4.5 의 "바뀌지 않은 문단은 분석하지 않는다" 가 실제로 성립한다.
- **파일 이름 NFC 정규화가 동작한다.** 대상 파일 이름에 한글이 들어 있는데도 감지에 성공했다.
  §2.4 에서 첫 관찰 시도를 실패하게 만든 함정을 넘겼다.

### 재현

기본 `npm run check` 에는 들어가지 않는다. 한글이 필요하기 때문이다.
위 명령으로 따로 돌린다. `V1_HWPX` 가 없으면 테스트는 실패가 아니라 건너뛰며,
건너뛴 사실을 출력에 남긴다.
