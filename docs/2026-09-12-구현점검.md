# 0~6단계 구현 점검 — 2026-09-12

## 결론

PRD·개발 원칙·단계 계획을 코드와 대조하고, 기존 테스트에 없던 실패 사례를 추가했다.
발견한 아래 오류를 수정했으며, 전체 자동 검사와 빌드는 통과했다.
이는 현재 구현된 범위의 검증 결과이지 MVP 전체 완료 선언은 아니다.

## 발견하고 수정한 문제

| 영역 | 문제 | 수정 |
| --- | --- | --- |
| 캐시 대상 연결 | 동일한 텍스트가 다른 문단에 있으면 다른 문단의 결과를 재사용할 수 있었다 | 문서·문단 식별자를 캐시 키에 포함하고 키 형식을 버전 관리 |
| 호출 이력 | 캐시 적중도 DB에는 모델 호출 1회로 기록했다 | 0회 저장 허용, 검토 요청 범위와 실제 전송 범위를 별도 기록 |
| 중복 요청 | 같은 문서에 동시 요청하면 캐시가 채워지기 전에 중복 호출했다 | 문서별 요청 직렬화, 후속 요청은 캐시 재확인 |
| 관점별 캐시 | 관점을 추가할 때 이미 검토한 관점까지 다시 보냈다 | 누락 관점이 같은 문단만 묶어 호출 |
| 캐시 복구 | 손상된 캐시 항목에서 예외가 나거나 정상 결과로 교체되지 않았다 | 재검증 실패 시 캐시 미스로 처리, 정상 결과로 교체 |
| 응답 병합 | 여러 캐시 결과를 합칠 때 모델 단일 응답의 30개 제한이 적용됐다 | 각 부분 응답 검증 후 별도 병합, 합산 결과 누락 방지 |
| 문장 검토 | 선택한 문장이 실제 모델 입력에서 빠졌다 | 선택 문장 정보를 전달하고 프롬프트를 `quick-review.v2`로 올림 |

| 반복 취약점 | 카드 수를 반복 취약점 관찰 횟수로 간주했다 | 임의 집계 제거. 8단계의 근거 있는 관찰 주입 전에는 0으로 계산 |
| 우선순위 | 전체를 정렬한 뒤 순위 번호로 다시 Top-K를 뽑았다 | 실제 점수로 안정적인 최소 힙 Top-K 구현 (`O(N log K)`) |
| 최신 문서 동기화 | 앱 종료 중 수정된 파일을 다시 열거나 재연결해도 이전 버전을 보였다 | 재선택·재연결·시작 시 감시 재개에서 최신 내용 동기화 |
| 버전 일관성 | 읽는 동안 저장되면 문단과 파일 해시가 다른 시점일 수 있었다 | 읽기 전후 해시 확인, 최초본 사본 검증 후 버전 기록 |
| 등록·재연결 실패 | 손상된 최초 파일이 빈 문서 기록을 남기거나 실패한 재연결이 경로를 바꿨다 | 최초 읽기·복사 성공 후 등록, 재연결 실패 시 기존 경로 보존 |
| 체크포인트 | 존재 확인 직후 다른 파일이 생기면 복사가 덮어쓸 여지가 있었다 | 배타적 복사로 덮어쓰기 차단, 크기 불일치 사본 정리 |
| HWPX 읽기 | 목차에 선언한 섹션이 누락돼도 일부만 읽고 성공했다 | 누락 섹션은 명시적으로 실패 처리 |
| 화면 갱신 | 저장 후 패널이 갱신되지 않거나 이전 문서의 늦은 응답이 새 화면을 덮었다 | 문서별 저장 알림 갱신, 화면 소유자·갱신 순번 검사 |
| 항목 경계 편집 | 추정 항목의 이름·범위만 바꿀 수 있어 통째로 묶인 문서를 나누지 못했다 | 항목 추가·삭제·순번 재정렬 제공, 저장 검증은 기존 경로 사용 |

## 검증 결과

- `npm run build` 통과: 계층 경계, TypeScript, ESLint, 테스트 **29개 파일 / 565개**, 메인·preload·renderer 빌드.
- `git diff --check` 통과.
- 실제 HWPX 샘플 **1개**에 대한 파싱·결정론·원본 불변·저장 감지 재현 테스트 **4개** 별도 재실행 통과.
- 기존 6번까지 적용한 SQLite에 검토·피드백을 넣은 뒤 7번 마이그레이션 적용 검증. 이력·외래키·멱등성·0회 호출 저장 확인.
- UI는 DOM 대역으로 항목 추가·삭제·저장, 문서 전환 응답 순서, 저장 알림 갱신을 검증했다. 실제 화면 배치 검증과는 다르다.

## 데이터 변경 안내

새 마이그레이션 `0007_review_audit.sql`을 추가했고, 이미 적용한 1~6번 SQL은 변경하지 않았다.
업데이트된 앱의 다음 DB 열기에서 신뢰할 수 없는 구 캐시만 무효화한다.
문서·버전·체크포인트·피드백 이력은 삭제하지 않는다. 캐시는 후속 검토에서 다시 채워진다.

과거 요청의 실제 전송 내역은 복원할 수 없으므로 새 전송 범위 필드를 `null`(알 수 없음)로 둔다.
과거 `attempts`는 원래 값을 보존한다. 새 기록부터 캐시 적중은 `attempts = 0`, 전송 범위는 빈 배열이다.
개발 테스트는 임시 파일·메모리 DB를 사용했으며 사용자의 앱 DB에 직접 마이그레이션하지 않았다.
8단계에 예정된 마이그레이션 파일명은 번호 충돌 방지를 위해 `0008_personalization.sql`로 조정했다.

## 남은 범위와 다음 확인

1. 실제 한글 for Mac에서 사본을 수정·저장하는 V-1 통합 테스트와 실제 Electron 화면 동작 확인.
   이번 검증은 실제 파일을 사용한 저장 동작 재현이며, 한글의 저장 버튼을 누른 검증은 아니다.
2. 실제 Gemma API 호출 품질·키체인 연동 확인. 이번에는 고정 응답과 가짜 전송으로 검증했으며 비용이 발생하는 호출은 하지 않았다.
3. 제목 스타일 판별은 실제 문서 미검증이라는 기존 제한이 남아 있다. 현재 실제 샘플은 1개이므로 본문 중심 샘플을 추가해 확인한다.
4. 문서 구조 기반 평가 지침 자동 초안은 `UNAVAILABLE_SUGGESTER` 상태다. 수동 입력·사용자 확정 경로는 구현되어 있지만 자동 초안까지 완료된 것은 아니다.
5. 8단계 자기평가·사용자 반응·반박·개인화·성장 요약, 9단계 개인 사용 마무리는 미구현이다.
   반복 취약점 점수의 실제 누적 관찰도 8단계에서 연결해야 한다. 7단계 Claude 심층 검토는 결정대로 보류한다.

이번 점검에서는 PRD나 확정된 제품 범위를 변경하지 않았다.
